## User-observable outcome

A pure, bounded small-machine admission guard: before the daemon admits new
agent/tool work it checks live-task, queue-depth, and byte-reservation counts
against the `config/resource-targets.json` acceptance profile and either admits
with a scoped reservation or rejects deterministically with
requested-vs-available figures. No process spawning, no thread, no I/O, no
telemetry emission. On the 2-core/4GiB fixture profile the default caps keep
one coding turn plus parked subagents inside the published targets; over-cap
work is refused, never queued unboundedly.

## Observable contract

- `OpsBudget { max_live_tasks: usize, max_queued: usize, max_input_bytes: u64, max_preview_bytes: u64 }`:
  `Default` mirrors resource-targets: `max_live_tasks: 4, max_queued: 256,
  max_input_bytes: 1048576, max_preview_bytes: 65536`.
- `Admission { live_tasks: u32, queued: u32, reserved_bytes: u64 }` (plain counters, caller-owned).
- `BudgetError::InvalidLimit(&'static str)` for any zero cap;
  `BudgetError::OverCap { requested: u64, available: u64 }` for refusals.
- `OpsBudget::validate(&self) -> Result<(), BudgetError>`: rejects any zero cap.
- `admit(live: u32, queued: u32, bytes: u64) -> Result<Admission, BudgetError>`:
  pure check, no mutation; admits iff `live < max_live_tasks`, `queued <
  max_queued`, `bytes <= max_input_bytes`.
- `reserve_preview(bytes: u64) -> Result<u64, BudgetError>`: admits iff `bytes
  <= max_preview_bytes`; returns granted bytes unchanged.
- Deterministic: same inputs => same verdict; no wall-clock, no env, no I/O.
- Suggested module boundary: NEW file `crates/foundation/src/ops_budget.rs`
  (pure functions only). Worker ships additive fragment only, never edits
  shared `lib.rs`, `Cargo.toml`, schemas, migrations. Integrator wires `pub mod`.
- Feature gating: none (pure policy helper; call sites gate subsystem
  construction per BASE-006 REQ-032 pattern).

## Failure states

- Zero cap in any field: `Err(BudgetError::InvalidLimit(name))`; no admission returned.
- Over live-task cap: `Err(OverCap { requested: live+1, available: max_live_tasks })`; caller counters unchanged.
- Over queue cap: `Err(OverCap { requested: queued+1, available: max_queued })`; nothing enqueued by this function.
- Oversize input/preview bytes: `Err(OverCap { requested: bytes, available: cap })`; no reservation held, no side effect.
- Arithmetic: `u64` counters use saturating/checked math; overflow can never
  admit (checked add failure => `OverCap` with `available: 0`).
- Secret safety: counters only, no paths/bodies logged. No SQLite/OpenCode DB
  writes. No changes to the user's existing OpenCode database; tests use
  in-memory counters only.

## Resource bounds

- O(1) time, O(1) memory; no allocation, no queue, no retained output.
- No thread, no task spawn, no detached work; caller owns `Admission` lifetime;
  cancellation is the caller's token, nothing to reclaim here.
- Whole-process-tree measurement (PLAN.md 9) stays a release-bench activity;
  this guard only refuses work that would exceed the published caps.

## Test obligations (frozen)

- OPS-007-T01 (defaults + happy path): `OpsBudget::default()` equals
  4/256/1048576/65536; `validate().is_ok()`;
  `admit(0, 0, 0).is_ok()`, `admit(3, 255, 1048576).is_ok()`;
  `reserve_preview(65536).unwrap() == 65536`.
- OPS-007-T02 (determinism): repeated `admit`/`reserve_preview` calls with same
  inputs return identical verdicts; verdict depends only on inputs, never on
  call order or wall-clock.
- OPS-007-T03 (caps refuse): `admit(4, 0, 0)` errs with
  `OverCap { requested: 5, available: 4 }`; `admit(0, 256, 0)` errs with
  `available: 256`; `admit(0, 0, 1048577)` errs with `available: 1048576`;
  `reserve_preview(65537)` errs with `available: 65536`.
- OPS-007-T04 (invalid limits): each zeroed field in turn =>
  `assert_eq!(err, InvalidLimit(name))`; `u64::MAX` byte request =>
  `OverCap` (never admit, never panic).
- OPS-007-T05 (no side effects + purity): failed `admit` mutates nothing
  (caller counters byte-identical before/after); captured logs contain zero
  input bytes; no test touches filesystem, network, env, or any DB.
