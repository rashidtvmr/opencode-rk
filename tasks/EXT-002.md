## User-observable outcome

Built-in native plugins wire through the same scoped lifecycle as EXT-001:
a fixed, auditable set of built-in plugin declarations is registered into a
caller-provided registry at startup, marked ready without any external host,
and removed cleanly on shutdown. No JavaScript host is started, no
filesystem scan is performed, no network is touched. External plugin
activation stays deferred (EXT-004 boundary); lifecycle add/remove/wait
semantics are owned by EXT-001, not redefined here.

## Observable contract

- `BUILTINS: &[(&str, &[&str])]`: fixed auditable table of built-in plugin
  name => capability labels. Initial table (frozen RED suite owns exact
  contents; exactly 2 entries, each with 0..=4 capabilities):
  `[("core.commands", &[]), ("core.skills", &["skill.list"])]`.
- `register_builtins(reg: &mut PluginRegistry, contract_version: u32)
  -> Result<Vec<PluginId>, PluginError>` (uses the EXT-001 `PluginRegistry`
  type; EXT-002 depends on the EXT-001 contract but introduces no new
  ordering dependency beyond test-double substitutability):
  registers every `BUILTINS` entry in table order with
  `contract_version == SUPPORTED_CONTRACT_VERSION`, then `mark_ready`s each;
  returns ids in table order. On first validation failure returns the
  EXT-001 typed error and rolls back any ids already added in this call
  (registry byte-identical to entry state).
- `unregister_builtins(reg: &mut PluginRegistry, ids: &[PluginId]) -> usize`:
  removes each id in order; returns count actually removed; unknown ids
  skipped harmlessly (mirrors EXT-001 remove-unknown semantics).
- `is_builtin(name: &str) -> bool`: `true` iff name is in `BUILTINS`.
  Dynamic (non-builtin) names never collide: `register_builtins` into a
  registry that already holds a same-named dynamic plugin returns
  `Err(Duplicate)` with no partial registration.
- Idempotence guard: second `register_builtins` into the same registry
  without an intervening `unregister_builtins` returns `Err(Duplicate)`;
  register -> unregister -> register yields fresh ids in table order.
- Deterministic: same table + same entry registry state => identical id
  sequences modulo the registry's own monotonic counter.
- Suggested module boundary: `crates/ext/src/builtins.rs` (same new crate
  `opencode-rk-ext` as EXT-001); worker ships additive fragment only, never
  edits shared `lib.rs`, `Cargo.toml`, schemas, migrations. Independent
  test owner: `crates/ext/tests/plugin_builtins.rs`. Tests may use the real
  EXT-001 registry or a frozen test double exposing the same
  add/mark_ready/remove/list contract.
- Runtime optional True: native mode starts no host either way; when the
  builtins feature flag is off, `register_builtins` is never called and
  zero builtin cost is incurred (mirrors TOOL-016 opt-out zero-cost proof).
- Explicitly excluded: external JS/TS host, executable plugin callbacks,
  hook execution (REQ-020), skill discovery/listing and filesystem traversal
  (unresolved partitions), UI presentation (REQ-005), file extraction
  (EXT-013), policy gating (TOOL-007), filesystem, network, persistence,
  environment lookup, credentials/secrets, HTTP routes, background work,
  new dependencies.

## Failure states

- Wrong `contract_version` passed: `Err(UnsupportedContract)`; registry unchanged.
- Name collision with an existing dynamic registration: `Err(Duplicate)`;
  no partial builtin registration (atomic per call).
- Double registration without unregister: `Err(Duplicate)`; registry unchanged.
- `unregister_builtins` with unknown ids: skips them, returns count of
  actually removed; never errors on unknown.
- Registry full (`MAX_PLUGINS` from EXT-001): `Err(Overflow)`; registry unchanged.
- Secret safety: builtin table holds names/capability labels only; nothing
  secret logged. No SQLite/OpenCode DB writes. No changes to the user's
  existing OpenCode database; tests use disposable in-memory registries only.

## Resource bounds

- Count caps: inherits EXT-001 `MAX_PLUGINS`; `BUILTINS.len() = 2` constant;
  rollback on failure guarantees no orphaned entries; no unbounded queue.
- Byte caps: inherits EXT-001 name/capability caps; the builtin table is
  `&'static` metadata, zero per-call allocation beyond the returned id vec
  (len 2); no unbounded retained output.
- Owner/cancel path: caller owns the registry and the returned id vec;
  both functions are synchronous with no cancel flag needed (bounded,
  constant-time, no blocking); no detached task, no background thread.
- Disabled path (feature off): `register_builtins` never called; zero
  allocation, zero threads, zero I/O; no hidden cost when off.

## Test obligations (frozen)

- EXT-002-T01 (happy path): empty registry + `register_builtins(reg, 1)`
  => `Ok(ids)`, `ids.len() == 2`, `list().len() == 2` in table order,
  every entry `state == Ready`, `is_builtin("core.commands")` and
  `is_builtin("core.skills")` are `true`, `is_builtin("evil")` is `false`.
- EXT-002-T02 (unregister clean): register => unregister with returned ids
  => returns `2`, `list()` empty; `unregister_builtins` with unknown ids
  only => returns `0`, registry unchanged; register -> unregister ->
  register => `Ok` again with fresh larger ids in table order.
- EXT-002-T03 (atomicity): pre-register dynamic decl named
  `"core.skills"` => `register_builtins` returns `Err(Duplicate)` and
  `list()` contains only the pre-existing dynamic entry (no partial
  builtins); double `register_builtins` without unregister =>
  `Err(Duplicate)`, `list().len() == 2` unchanged; wrong version `999` =>
  `Err(UnsupportedContract)`, registry unchanged.
- EXT-002-T04 (no lifecycle redefinition): register builtins, then use the
  EXT-001 contract directly: `wait_ready(ids[0], unset_flag)` => `Ok(())`;
  removing one builtin id via the registry leaves the other `Ready` and
  visible; re-registering after partial removal returns `Err(Duplicate)`
  for the still-present name with no partial add.
- EXT-002-T05 (zero cost when off + safety): with builtins disabled, assert
  `list()` empty, no threads spawned, no files created outside the
  disposable test dir, no DB writes; captured logs contain zero builtin
  capability strings beyond the two audited names and zero
  credential-like bytes.
