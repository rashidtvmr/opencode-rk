## User-observable outcome

Native plugin manifest validation for one caller-owned declaration at a time:
callers submit bounded manifest bytes (JSON) and get a typed accept/reject
without touching a registry, starting a JavaScript host, activating any
plugin, or writing any state. Accepted manifests carry a validated name,
contract version, and capability list that later lifecycle/bridge slices
(EXT-001/003/007) may consume. Rejected manifests leave nothing behind.
Reload/watch, external JS/TS activation, skill/command discovery, hook
execution, UI presentation, and legacy V1 config lowering are explicitly out
of scope.

## Observable contract

- `SUPPORTED_CONTRACT_VERSION: u32 = 1` (must equal EXT-001 value).
- `MAX_MANIFEST_BYTES: usize = 16384`; `MAX_NAME_LEN: usize = 128`;
  `MAX_CAPABILITIES: usize = 16`; `MAX_CAP_LEN: usize = 64`.
- `Manifest { name: String, contract_version: u32, capabilities: Vec<String> }`.
  Name: 1..=128 chars, `[A-Za-z0-9][A-Za-z0-9._-]*`. Capabilities: 0..=16
  entries, each 1..=64 chars, same charset; intra-manifest duplicates rejected.
- `validate_manifest_bytes(bytes: &[u8]) -> Result<Manifest, ManifestError>`.
  Pure function: no registry, no I/O, no threads, no global state.
  Steps in order: length check (`bytes.len() <= MAX_MANIFEST_BYTES`),
  UTF-8 check, JSON parse (`{name: string, contract_version: u32,
  capabilities?: string[]}`; unknown fields ignored), field validation.
- `validate_manifest(m: &Manifest) -> Result<(), ManifestError>` exposed for
  struct-level checks without parsing.
- Deterministic: same input bytes => identical verdict; no wall-clock, no ids.
- Suggested module boundary: new pure module `crates/ext/src/manifest.rs`
  (crate `opencode-rk-ext`); worker ships additive fragment only, never edits
  shared `lib.rs`, `Cargo.toml`, schemas, migrations. Independent test owner:
  `crates/ext/tests/plugin_manifest.rs`.
- Explicitly excluded: registry add/remove/wait (EXT-001), reference bridge
  (EXT-003), integration bridge (EXT-007), hook execution (REQ-020:
  SEC-010/SEC-011/SEC-020/EXT-008), skills/commands internals, UI
  presentation (EXT-009/EXT-012/UI-012), legacy V1 lowering and event-wire
  compatibility (INT-008), filesystem, network, persistence, environment
  lookup, credentials/secrets, HTTP routes, background work, new dependencies.

## Failure states

- Too large (`bytes.len() > MAX_MANIFEST_BYTES`):
  `Err(ManifestError::TooLarge)`; nothing parsed, nothing allocated beyond input.
- Non-UTF8 bytes: `Err(ManifestError::InvalidEncoding)`; no partial value returned.
- Malformed JSON / wrong shape: `Err(ManifestError::InvalidJson)`; no partial value.
- Invalid name (empty, too long, bad charset, missing):
  `Err(ManifestError::InvalidName)`.
- Bad capabilities (too many, bad entry, intra-manifest duplicate, wrong type):
  `Err(ManifestError::InvalidCapabilities)`.
- Unsupported contract version (`!= SUPPORTED_CONTRACT_VERSION`, missing,
  non-u32): `Err(ManifestError::UnsupportedContract)`.
- All errors are pure verdicts; no state exists to mutate. No panic on any
  input up to 1 MiB (fuzz-adjacent negative test feeds oversize/binary inputs).
- Secret safety: manifest holds names/capability labels only; nothing secret
  is logged. No SQLite/OpenCode DB writes. Tests use in-memory byte slices only.

## Resource bounds

- Byte cap: `MAX_MANIFEST_BYTES` checked before parse; parser input bounded;
  retained `Manifest` bounded by name/capability caps (max ~1152 bytes +
  struct overhead); no unbounded retained output.
- No queue, no map, no cache: pure function, zero retained state between calls.
- Owner/cancel path: caller owns input bytes and returned `Manifest`; no
  cancellation token needed (synchronous, sub-millisecond on capped input);
  no detached task, no background thread, no host process.
- Zero hidden cost: validation allocates only the returned struct; no threads,
  no watchers, no registry.

## Test obligations (frozen)

- EXT-005-T01 (happy path): three valid JSON manifests (0 caps, 1 cap,
  16 caps) => `Ok`, `manifest.name` equals input, `capabilities.len()`
  equals input count, `contract_version == 1`; unknown extra JSON field
  ignored and still `Ok`.
- EXT-005-T02 (determinism + struct entry): same bytes validated twice =>
  byte-identical `Manifest` values; `validate_manifest(&good)` => `Ok(())`;
  missing `capabilities` key defaults to `[]` deterministically.
- EXT-005-T03 (field validation): empty name => `Err(InvalidName)`; 129-char
  name => `Err(InvalidName)`; bad charset (`"a/b"`, `" a"`) =>
  `Err(InvalidName)`; 17 capabilities => `Err(InvalidCapabilities)`;
  intra-manifest duplicate cap => `Err(InvalidCapabilities)`;
  `contract_version: 999` => `Err(UnsupportedContract)`; each case asserts
  the exact variant via `assert_eq!(err, ...)`.
- EXT-005-T04 (byte-layer failures): 16385-byte input => `Err(TooLarge)`;
  non-UTF8 bytes (`b"\xff\xfe{"`) => `Err(InvalidEncoding)`; truncated JSON
  (`b"{\"name\":"`) => `Err(InvalidJson)`; JSON array input (`b"[]"`) =>
  `Err(InvalidJson)`; 1 MiB binary blob => `Err(TooLarge)` without panic and
  completes promptly (<1 s).
- EXT-005-T05 (no side-effect safety): run full matrix while asserting no
  files created outside the disposable test dir, no test writes to any DB
  path, no child process spawned; captured logs contain zero capability
  strings beyond the manifest name and zero credential-like bytes.
