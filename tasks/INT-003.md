# INT-003 - Provider-specific integration method dispatch boundary

Status: NOT STARTED. Kind: product. Runtime optional: False.
Mandatory for full declared release: yes.
Requirements: none (DISC-002 discovered `opencode.integrations` residual; deferred per `opencode.integration-auth` finding).
Dependencies: none.
Test obligations: INT-003-T01, INT-003-T02, INT-003-T03, INT-003-T04, INT-003-T05.

## User-observable outcome

Native code can enumerate which provider-specific integration methods exist,
dispatch a typed method call (`key` / `oauth` / provider-named) to exactly one
registered provider implementation, and reject unknown providers or methods
with a typed error. No secret material is stored, no network or OAuth callback
executes, no event is published here. Provider execution internals stay behind
the dispatch boundary.

## Observable contract

- `ProviderMethodKind`: `Key` | `OAuth` | `Env` | `ProviderNamed { provider: ProviderId, method: MethodName }`.
  `ProviderId`/`MethodName` are validated non-empty `a-z0-9-_` strings,
  max 64 bytes each; anything else is rejected before registration.
- `MethodTable::register(provider, method, handler_id) -> Result<(), MethodError>`:
  bounded static table, `MAX_PROVIDERS = 64`, `MAX_METHODS_PER_PROVIDER = 16`;
  duplicate `(provider, method)` replaces deterministically in place;
  overflow returns `Err(MethodError::TableFull)` with no mutation.
- `dispatch(provider, method, input: &MethodInput) -> Result<MethodReceipt, MethodError>`:
  routes to exactly one registered handler id and returns an opaque receipt
  (`handler_id`, `accepted: bool`); unknown provider => `Err(MethodError::UnknownProvider)`;
  unknown method => `Err(MethodError::UnknownMethod)`. Dispatch itself performs
  no network, secret storage, env read, or event publish; execution (if any) is
  the caller's authority behind the returned receipt.
- `list_methods(provider) -> Vec<MethodName>` sorted; `providers() -> Vec<ProviderId>` sorted.
  Deterministic: same registration order-insensitive set => identical sorted output.
- Suggested module boundary: new `crates/providers/src/int_methods.rs`
  (additive fragment only). Worker never edits shared `lib.rs`, `Cargo.toml`,
  schemas, or migrations; integrator wires exports.
- Caller owns handler execution, secrets, env, persistence, network, and events.

## Failure states

- Unknown provider/method: typed `UnknownProvider`/`UnknownMethod`; no side effect,
  no partial registration, no log of secret bytes.
- Invalid id (`empty`, `>64 bytes`, bad charset): `Err(MethodError::InvalidId)`; table unchanged.
- Table full: `Err(MethodError::TableFull)`; existing entries untouched, no eviction.
- Secret safety: method inputs carry opaque handles only; full key/token bodies never
  retained or logged. No SQLite/OpenCode DB writes. No changes to the user's existing
  OpenCode database; tests use disposable fixture state only.

## Resource bounds

- Count caps: 64 providers x 16 methods bound the table; no unbounded queue or map
  (no 10-minute attempt map, no 30-second scrubber, no background fiber in this slice).
- Byte caps: ids bounded (64 B); `MethodInput` borrows caller bytes, max 4 KiB
  inspected; nothing retained after dispatch returns.
- Owner/cancel path: synchronous dispatch, no detached task, no thread; caller owns
  all lifetimes; drop of table frees everything.
- Zero hidden cost when empty: default table allocates nothing until first register.

## Test obligations (frozen)

- INT-003-T01 (register + dispatch happy path): register 2 providers x 2 methods;
  `assert_eq!(table.providers().len(), 2)`, `assert_eq!(list_methods(p).len(), 2)`,
  `dispatch(p, m, &input)` returns `Ok(receipt)` with `receipt.handler_id == expected`
  and `receipt.accepted`.
- INT-003-T02 (determinism + ordering): two tables built in different registration
  order: `assert_eq!(t1.providers(), t2.providers())`,
  `assert_eq!(t1.list_methods(p), t2.list_methods(p))` (sorted); duplicate register
  replaces: `assert_eq!(len_after, len_before)` and dispatch hits the new handler id.
- INT-003-T03 (caps hold): fill to 64 providers (or 16 methods on one provider);
  next register => `assert_eq!(err, TableFull)`, `assert_eq!(len(), cap)`;
  bulk dispatch of 10k calls completes without growth (`len()` unchanged, no OOM).
- INT-003-T04 (failure states): unknown provider => `assert_eq!(err, UnknownProvider)`;
  unknown method => `assert_eq!(err, UnknownMethod)`; invalid id (empty / 65 bytes /
  `UPPER SPACE!`) => `assert_eq!(err, InvalidId)`; failed calls leave `len()` unchanged
  and produce zero handler executions (counter stays 0).
- INT-003-T05 (no side effects + safety): dispatch performs no I/O (assert no FS/DB
  writes outside disposable fixture dir); captured logs contain zero input-handle
  bytes; unknown-method error path asserts absence of handler execution, not just
  an error string.
