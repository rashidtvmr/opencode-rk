## Contract decisions before RED

- Native bridge carries only `IntegrationInfo` and `IntegrationMethod::{Key, OAuth}` metadata already owned by INT-004.
- Plugin scope lifetime is caller-owned and uses existing `close_scope` reveal/removal semantics.
- A declaration is applied atomically: any invalid metadata/capacity error leaves the registry exactly as it was before the call.
- Existing bounds (`MAX_INTEGRATION_SCOPES`, `MAX_INTEGRATIONS_PER_SCOPE`, `MAX_INTEGRATION_METHODS`, metadata byte caps) are reused rather than introducing an unapproved resource class.
- No JS runtime, callback/function storage, OAuth execution/refresh, env lookup, credentials, network, persistence, HTTP, background work, or new dependency.

## Implementation

- Added inert `PluginIntegrationRegistration` and `PluginIntegrationDeclaration` metadata types in the existing provider integration module; neither type contains callbacks, secret material, env names, network handles, or persistence state.
- `IntegrationRegistry::register_plugin_scope` rejects declaration integration count and per-registration method count in O(1) length checks using the existing public caps before iterating caller data.
- The bridge then applies the bounded declaration to a clone of `IntegrationRegistry` using the already-tested `register` / `set_method` validation and scoped replacement semantics. `self` is replaced only if the entire declaration succeeds, so invalid ids/labels, method capacity errors, scope capacity errors, or other typed validation failures are atomically non-mutating.
- Same-id OAuth updates replace in their existing slot and the single key slot replaces in place through INT-004 semantics; registration order remains deterministic.
- Plugin lifetime remains caller-owned through the existing scope token and `close_scope`; no background owner or cleanup task was added.
